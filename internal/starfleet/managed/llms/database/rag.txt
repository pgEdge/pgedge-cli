##### pgedge starfleet managed database rag

Manage the RAG server deployed alongside a managed database: the
retrieval-augmented-generation pipelines built over its data.

**Example:**

```bash
pgedge starfleet managed database rag deploy <database_id> \
  --embedding-llm-provider openai \
  --embedding-llm-model text-embedding-3-small \
  --embedding-llm-api-key "$OPENAI_API_KEY" \
  --completion-llm-provider openai \
  --completion-llm-model gpt-4o \
  --completion-llm-api-key "$OPENAI_API_KEY" \
  --pipeline-config pipelines.json
pgedge starfleet managed database rag update <database_id> --top-n 10
pgedge starfleet managed database rag apply <database_id> --top-n 10
```

`pgedge llms starfleet managed connecting-a-client` carries the RAG
endpoint's shape and how it authenticates.

###### pgedge starfleet managed database rag deploy

Stand up a RAG server on a database.

**`deploy` creates the service.** If one is already deployed on this
database, it exits 1 and names `rag update` as the fix, rather than
silently reconfiguring it — no PATCH is sent.

Both LLM settings and a pipeline config are required, because the API
requires all three and rejects a partial config outright.

**A new service's endpoint is closed.** `--allow <cidr>`
(repeatable), `--my-ip` and `--open` set its allowlist in the deploy
request itself, as the `allowlist` page describes. With none of them
the service starts closed, and `database allowlist add <database_id>
--service rag` admits an address afterward.

`--pipeline-config` points at a JSON file holding the pipeline
definitions. It accepts either a bare array of pipelines or an object
with a `pipelines` key — the latter is the shape the API returns, so a
config read back from `database get` can be pasted straight into a
file. The CLI validates names, duplicate names and each pipeline's
tables before sending.

**Anything wrong with that file is exit 2, not 1.** A path with no file
on it, a path that is a directory, JSON that does not parse, an object
without a `pipelines` key, and every structural rule checked after the
parse all report the same code, because they are all the same mistake:
the input you handed the command. No write is sent in any of them, but
the database GET that precedes the file read has already gone out. The
completeness guard on the LLM flags — `... is required to deploy a RAG
service` — is exit 2 too. `rag update` answers identically for the same
file.

Exit 0 means the API accepted the deploy, not that the server is
serving, and the service `state` field cannot tell you which — it
reads `running` either way. How long RAG takes to converge is not
known: unlike MCP it has no readiness handshake to measure against.

**Example:**

```bash
pgedge starfleet managed database rag deploy e5f6a7b8-c9d0-1234-efab-567890123456 \
  --embedding-llm-provider openai \
  --embedding-llm-model text-embedding-3-small \
  --embedding-llm-api-key sk-... \
  --completion-llm-provider anthropic \
  --completion-llm-model claude-sonnet-5 \
  --completion-llm-api-key sk-ant-... \
  --pipeline-config pipelines.json
```

###### pgedge starfleet managed database rag update

Change the RAG server's configuration.

**`update` requires a deployed RAG service.** If none is deployed on
this database, it exits 1 and names `rag deploy` as the fix.

Only the flags you pass are changed; the deployed pipelines and every
other setting are read back and preserved.

**The LLM API keys may be omitted.** The API never returns them, and
refills an omitted key from the service's stored state on an update.
Pass `--embedding-llm-api-key` or `--completion-llm-api-key` only to
rotate one.

`--top-n 0` and `--token-budget 0` are honored as explicit zeros, not
treated as unset.

**Example:**

```bash
pgedge starfleet managed database rag update e5f6a7b8-c9d0-1234-efab-567890123456 \
    --top-n 10
pgedge starfleet managed database rag update e5f6a7b8-c9d0-1234-efab-567890123456 \
    --pipeline-config pipelines.json
pgedge starfleet managed database rag update e5f6a7b8-c9d0-1234-efab-567890123456 \
    --completion-llm-api-key sk-ant-...
```

**`--wait` proves the write finished, not that the running pipeline
reflects the change.** The `update-managed` task settles before the
running pipeline does, so even with `--wait`, a script that updates a
pipeline and immediately queries it should tolerate briefly seeing the
old configuration. Without `--wait` the verb exits 0 the moment the API
accepts the change.

###### pgedge starfleet managed database rag apply

Deploy a RAG server when the database has none, and update the
deployed one otherwise, in one command with one exit status. Use it
wherever a script would otherwise choose between `deploy` and
`update`.

`apply` reads the database first. A read that fails ends the command
with that read's exit status and sends no write, so an authentication
failure, a network error or an unknown database ID never becomes a
deploy.

`apply` takes `deploy`'s and `update`'s flags. A new service needs
every flag `deploy` marks required, and a missing one is exit status 2
naming it, with nothing sent. On a deployed service only the flags you pass
change, as on `update`, and the LLM API keys may be omitted.

`--allow`, `--my-ip` and `--open` set a new service's allowlist, as on
`deploy`. On a deployed service they are exit status 2 with nothing
sent, and the error names `database allowlist add <database_id>
--service rag`
as the command for its rules.

**Example:**

```bash
pgedge starfleet managed database rag apply e5f6a7b8-c9d0-1234-efab-567890123456 \
    --top-n 10 --wait
pgedge starfleet managed database rag apply e5f6a7b8-c9d0-1234-efab-567890123456 \
  --embedding-llm-provider openai \
  --embedding-llm-model text-embedding-3-small \
  --embedding-llm-api-key "$OPENAI_API_KEY" \
  --completion-llm-provider openai \
  --completion-llm-model gpt-4o \
  --completion-llm-api-key "$OPENAI_API_KEY" \
  --pipeline-config pipelines.json --my-ip --wait
```
