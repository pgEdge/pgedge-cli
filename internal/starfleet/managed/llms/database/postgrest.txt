##### pgedge starfleet managed database postgrest

Manage the PostgREST API deployed alongside a managed database: the
REST interface generated from its schemas.

**Not yet supported on managed databases.** The platform rejects the
`postgrest` service type outright, so `deploy` always fails with a
400. Since no PostgREST service can ever be deployed, `update` always
ends in the deploy/update guard at exit 1, but only if it gets that
far, and three things come first. A malformed database id or an
out-of-range `--db-pool`, `--max-rows` or `--jwt-secret` is refused
at exit 2 with no request sent at all. Then credentials resolve, so
`update` with none configured exits 5. Then the database is read, so
an unreachable API or an id that does not exist answers there. The
guard is last. `mcp` and `rag` are the service types
that deploy. The commands stay documented below for their
intended usage once the platform accepts the service type.

**Example:**

```bash
pgedge starfleet managed database postgrest deploy <database_id> \
  --db-schemas public --db-anon-role app_read_only
pgedge starfleet managed database postgrest update <database_id> --max-rows 500
```

###### pgedge starfleet managed database postgrest deploy

Stand up a PostgREST API on a database.

Not yet supported on managed databases: the platform rejects the
service type, so this currently fails with a 400. `mcp` and `rag`
are the service types that deploy.

**`deploy` creates the service.** The deploy/update guard applies
unchanged even though the service type is not yet accepted: if a
PostgREST service were already deployed on this database, `deploy`
would exit 1 and name `postgrest update` as the fix, rather than
silently reconfiguring it.

`--db-schemas` and `--db-anon-role` are required: they decide what is
exposed and which role unauthenticated requests run as.

`--db-pool` accepts 1-30 and `--max-rows` accepts 1-10000; the CLI
rejects anything outside those bounds at exit 2, before a credential is
resolved. `--jwt-secret` must be at least 32 characters, checked the
same way. So are `--db-schemas` and `--db-anon-role` on `deploy`: an
explicitly empty value satisfies the required-flag rule and is refused
here instead.

**Example:**

```bash
pgedge starfleet managed database postgrest deploy e5f6a7b8-c9d0-1234-efab-567890123456 \
  --db-schemas public --db-anon-role app_read_only
pgedge starfleet managed database postgrest deploy e5f6a7b8-c9d0-1234-efab-567890123456 \
  --db-schemas public,api --db-anon-role app_read_only \
  --max-rows 500 --jwt-secret <32-char-minimum-secret>
```

###### pgedge starfleet managed database postgrest update

Change the PostgREST API's configuration.

Not yet supported on managed databases: the platform rejects the
service type outright, so `deploy` always fails with a 400 and no
PostgREST service can ever be deployed to update. `mcp` and `rag`
are the service types that deploy.

**`update` requires a deployed PostgREST service.** Since none can be
deployed, `update` exits 1 client-side (naming `postgrest
deploy`) rather than reaching the platform's 400, because the guard
fires first.

One check comes before that guard: `--db-pool`, `--max-rows` and
`--jwt-secret` are range-checked at exit 2 before a credential is
resolved, so a value outside its bounds answers 2 and never reaches
the guard at all. The same bounds apply on `deploy`.

Only the flags you pass are changed; everything else is read from the
deployed service and preserved.

`--jwt-secret` is write-only: the API never returns it, and keeps the
stored secret when an update omits it. Pass `--jwt-secret` only to
rotate it.

**Example:**

```bash
pgedge starfleet managed database postgrest update e5f6a7b8-c9d0-1234-efab-567890123456 --max-rows 500
pgedge starfleet managed database postgrest update e5f6a7b8-c9d0-1234-efab-567890123456 --db-schemas public,api
```
