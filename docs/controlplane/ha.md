# High availability operations

Three operations keep a Control Plane database available: moving its
leader between nodes, taking single Postgres instances in and out of
service, and removing a host that is never coming back. Every
operation here acts on a database a Control Plane already runs, and
each one hands the real work to a task you then watch.

You need a Control Plane cluster the CLI can reach and a database on
it. The [Control Plane standup workflow](local-server.md)
covers getting the server running and the cluster initialized, and
the [Control Plane databases guide](databases.md) covers writing a
spec and creating the database. This CLI supports
Control Plane 0.10.0 and later.
`pgedge controlplane doctor` turns its Reachable row into a warning
when a server reports a version below that floor.

## Read the instances before you act

The commands below take either a node name or an instance ID, and the
two are not interchangeable. `node switchover` and `node failover`
name a node, such as `n1`. The three instance commands name an
instance, and so does `--candidate` on both node commands.

Instance IDs are generated by the server as
`<database>-<node>-<suffix>` with a random suffix, so you cannot build
one from a database and a node name. Read them from the fleet instead:

    pgedge controlplane database instance list --database storefront

The table carries DATABASE, ID, NODE, HOST, STATE, ROLE, PG and SPOCK
columns, and the ID column is the value every other instance command
wants. Dropping `--database` lists every instance in the cluster, and
`pgedge controlplane database get storefront` shows the same IDs for
one database. A `--database` that names nothing exits 4, while a real
database holding no instances reports that on `stderr` and exits 0, so
a mistyped name cannot pass for an empty database. Under `-o json` an
empty result is `[]` rather than nothing, so a filter reading it still
gets a document.

## Planned switchover

A switchover promotes a replica to leader gracefully, on a database
that is healthy. It drops the connections the old leader was holding,
so a connected application notices.

The following command promotes a named replica and blocks until the
task finishes:

    pgedge controlplane database node switchover storefront n1 \
        --candidate storefront-n2-9ptayhma --force --wait

`--candidate` chooses which replica is promoted, and the CLI validates
nothing about it. A wrong or misspelled instance ID is sent as it
stands, so whatever the server makes of it arrives after the call
rather than as a usage error before it. Take the value from
`instance list`. Omitting the flag leaves the choice to the Control
Plane.

`--scheduled-at` defers the change to an RFC3339 time. The CLI parses
it before it prompts, so a malformed timestamp is a usage error at
exit 2 rather than a question about an operation that cannot run.

Switchover always prompts. Run it non-interactively without `--force`
and it stops at exit 2, saying the operation is destructive and asking
for `--force` or an interactive terminal.

## Unplanned failover

A failover is the unplanned move, for a leader that is already
unhealthy. It can interrupt writes, so prefer a switchover whenever
the current leader is still answering.

The following command fails a node over and streams the task log:

    pgedge controlplane database node failover storefront n1 \
        --force --follow

The Control Plane runs health checks that block a failover on a
healthy cluster, and `--skip-validation` bypasses them. Reach for that
flag only when you know the leader is gone and the checks disagree.

Failover validates nothing at all on the client. `--candidate` is
unchecked here as it is on switchover, and there is no
`--scheduled-at` to get wrong, so every rejection arrives from the
server or inside the task. Like switchover, it always prompts.

## Start, stop and restart an instance

The instance commands act on the per-host Postgres container behind
one node, rather than on the node's replication role. The following
table shows what each command does and how it treats confirmation:

| Command | What it does | Prompts | Other flags |
|---|---|---|---|
| `start` | Brings a stopped instance back online. | No | `--force-unmodifiable` |
| `stop` | Takes an instance out of the database until it is started again. | Yes | `--force`, `--force-unmodifiable` |
| `restart` | Bounces the instance's Postgres process, dropping its connections. | Yes | `--force`, `--scheduled-at` |

The following command restarts one instance during a maintenance
window:

    pgedge controlplane database instance restart storefront \
        storefront-n1-689qacsi --force --scheduled-at 2026-09-01T22:00:00Z

Only `restart` takes `--scheduled-at`, and the asymmetry is the API's
rather than the CLI's. Start and stop are query-parameter endpoints
with no body to carry a schedule, while restart takes a body with a
`scheduled_at` field. A scheduled restart is confirmed when you queue
it, not when it runs.

`instance list` is a plain read: it spawns no task and takes neither
`--wait` nor `--follow`.

## The three force flags

Three flags in this tree start with `--force`, and they do different
things. The following table shows which commands across the whole
controlplane module take each one, and what it changes:

| Flag | Commands | What it changes |
|---|---|---|
| `--force` | `node switchover`, `node failover`, `instance stop`, `instance restart`, `host remove`, `database restore`, `database delete`, `database upgrade`, `task cancel` | Skips the confirmation prompt in the CLI. It is never sent to the server. |
| `--force-unmodifiable` | `instance start`, `instance stop`, `node backup`, `database restore`, `database delete` | Sets the API's own force parameter, so the server waives its unmodifiable-state check. |
| `--force-lost` | `host remove` | Sets that same API parameter on host removal, so the server waives the instance and quorum checks. |

So `--force` alone never overrides a server-side check, and a scripted
`host remove --force` skips the question without opting into the
quorum waiver. A command that never prompts carries no `--force` at
all: `node backup` and `instance start` both reject it as an unknown
flag at exit 2.

## Remove a host

`host list` and `host get` show the cluster's hosts with ID,
ORCHESTRATOR, STATE and UPDATED columns. STATE is one of `healthy`,
`unreachable`, `degraded` or `unknown`. UPDATED is a date with no time
of day, so it cannot tell you a status went stale this morning. Read
`-o json` when that matters. `host get` prints a single row in the
same shape as the list rather than a field-by-field block:

    pgedge controlplane host list
    pgedge controlplane host get host-3

`host remove` takes a host out of the cluster. This is destructive,
because databases with instances on that host are affected, so the
command prompts unless `--force`.

The server then applies a precondition of its own, and it has nothing
to do with whether the host still answers: the removal is refused
while instances live on the host, or when losing the host would break
quorum. `--force-lost` waives both checks, so it can leave a database
short of an instance and a cluster short of a voter. That is the
disaster-recovery path, for a host that is permanently gone. An
unreachable host may come back, so use `--force-lost` only for one
that will not.

The following command removes a lost host and waits for the removal
task:

    pgedge controlplane host remove host-3 --force --force-lost --wait

The removal is asynchronous like everything else here, with one
difference that matters when you go looking for the task afterward:
it is a host task, not a database task. Read it with
`pgedge controlplane task get --host host-3 <task_id>`. Under
`-o json` or `-o yaml` the accepted response carries the removal task
under `task` and any database updates the removal spawned under
`update_database_tasks`.

## Watching tasks

Every command on this page except `instance list`, `host list` and
`host get` spawns a task and returns as soon as the server accepts it.
Acceptance is a line on `stderr` reading `Switchover task <id>
accepted (<status>).`, with the command's own name in front. `host
remove` is the one that words it differently, as `Host removal task
<id> accepted (<status>).`.

Under `-o json` or `-o yaml` the API's accepted response object also
goes to `stdout`, exactly once, in every wait mode. Progress lines and
the terminal verdict stay on `stderr`, and text output writes nothing
to `stdout` at all. The
[output formats and paging guide](../output-and-paging.md) covers that
split across the whole CLI.

`--wait` blocks until the task reaches a terminal state, printing one
status line per poll to `stderr`. It defaults to a 600-second bound
and a three-second interval, and an interval below one second is
treated as one second. Its own bound is not the only one in play: a
single poll that outlives `--timeout`, 30 seconds by default, aborts
the wait at exit 3 rather than retrying on the next interval.

`--follow` streams the task's log instead, and it ignores both wait
flags. It applies no overall bound, polls every two seconds rather
than on `--wait-interval`, and bounds each individual log poll at 30
seconds independently of `--timeout`. So `--timeout 0` still stops a
poll at 30 seconds, and only a `--timeout` below 30 seconds shortens
one.

The two also report a failure differently. `--wait` prints
`task <id> failed: <reason>` when the task carries a reason, while
`--follow` prints a bare `task <id> failed` and leaves the reason to
be looked up. Either way,
`pgedge controlplane task get --database storefront <task_id>` holds
the reason and `task logs` holds the step trace.

A third terminal outcome sits alongside `completed` and `failed`:
`canceled`. Both wait modes treat it as a failure at exit 1 on every
command here, reporting that the task was canceled. `task cancel` is
the exception, because there a canceled task is the outcome you asked
for. `canceling` is a status rather than an outcome, so a wait keeps
polling through it until the task settles. The
[tasks and async operations guide](../tasks-and-async.md) covers task
inspection and cancellation for all three modules.

Each mutating command here also takes `--dry-run`, which runs the
client-side checks, reports the request it would have sent, and stops
before sending it. A controlplane dry run consults no server at all.
It validates a spec locally on `database create` and `database
update`, and on the commands here there is nothing left for it to
check but the confirmation, so it prints the request it would have
sent and says the server was not consulted. It never prompts either,
and unless you pass `--force` as well it records the confirmation the
real run would have asked for. The [dry runs guide](../dry-run.md)
has the detail.

## Exit codes

The following table shows what produces each exit code on this page:

| Code | What produces it here |
|---|---|
| 0 | The server accepted the operation, and under `--wait` or `--follow` the task completed. |
| 1 | The task failed or was canceled, the Control Plane could not be reached, or the server refused the operation with any status other than the four below. |
| 2 | A usage error: a malformed `--scheduled-at`, a destructive command run non-interactively without `--force`, or `--force` passed to a command that never prompts. |
| 3 | A bound expired: `--timeout` on one request, `--wait-timeout` on a wait, or the 30-second log poll under `--follow`. A 408 or 504 from the server lands here too. |
| 4 | The database, node, instance or host does not exist. The server usually says so in a JSON error, though `instance list --database` decides it locally from the database list. |
| 5 | The server answered 401 or 403, which in front of a Control Plane usually means a proxy rather than the Control Plane itself. |

Exit 1 covers two further cases. A cluster that was never initialized
answers 409 on every command here, and the CLI says so and points at
`cluster init`.
A 404 carrying the router's plain `404 page not found`, rather than a
JSON error, means the server does not serve the endpoint at all, which
is what a Control Plane below the 0.10.0 floor looks like from here.
Both exit 1, not 4.

The [exit codes reference](../exit-codes.md) carries the contract for
every module, and the [health checks guide](../doctor.md) explains the
`doctor` rows to read first when a command cannot connect.
