# Connecting a client to a deployed MCP or RAG service

> A topic page of the `starfleet managed` reference. A deployed service
> is reached outside the CLI, and this page is how to find its address
> and credential and know it is ready. `pgedge llms starfleet managed`
> is the index.

A deployed service is reached at the URL the API reports in the
service's `uri`. Ask the API for it rather than assembling it: `service
list`, `service get` and `database get` print it as ENDPOINT in their
tables, `-o json` carries the field itself, and there is no port in
it. Before dialling, admit the caller's address on that service's own
allowlist: a freshly deployed service starts closed, and `allowlist
add <database_id> <cidr> --service mcp` (or `rag`) is the command. A
caller the allowlist does not admit gets 403 whatever it sends.

A table never prints a secret, so MCP's bearer token needs `mcp
connection` or `-o json`. `database get`, `service get` and `service list` all read the
single-database GET, which is the path that returns service secrets.
`database list` does not, so a configuration built from a list entry
arrives with its secrets blank, indistinguishable from a service that
has none. Read a single database before building a configuration from
one.

## MCP

A deployed MCP server speaks streamable-HTTP MCP at `POST <uri>`, where
the `uri` is `https://<domain>/mcp/v1`, and expects a bearer token,
forwarded to the server as `INIT_TOKENS`. That token is whatever was
passed to `--init-tokens` at deploy time, generated by the API when the
flag was omitted, or rotated afterward with `mcp update`. `mcp
connection <database_id>` prints the current `uri` and token, and
nothing else from the database. `database get -o json` returns the
same token inside the `services` entry whose `service_type` is `mcp`,
in that entry's `mcp_config` block, beside the database password.

**A branch's MCP server is a different server.** It has its own `uri`
and its own bearer token, both printed by `mcp connection
<database_id> --branch <branch_id>`. The source database's token is
refused with 401 at the branch's endpoint, so a client pointed at a
branch needs the branch's values, not the source's. Its allowlist is
the source's MCP allowlist as it stood when the branch was created,
and it never changes afterward.

The transport requires an `Accept: application/json,
text/event-stream` header, and the first request on a connection must
be an `initialize` call: a cold `tools/list` is a lifecycle violation.
A server may return an `Mcp-Session-Id` header, which later requests on
the same session echo back. `notifications/initialized`, then
`tools/list`, follow on the same session once `initialize` succeeds.

**Readiness is the service's answer, not a status.** A service's
`state` reads `running` as soon as the deploy completes, while the
endpoint can still answer 503, and an update or a removal also takes
effect on the endpoint after its task succeeds, not with it. A new
branch's MCP endpoint answers 503 with the plain-text body `no
available server` even after `database branch create --wait` returns.
Retry `initialize` until it answers 200, and act on a `failed`
`state`, never on `running`.

`mcp connection -o json` prints an object holding `uri` and `token`.
It ends with exit status 1 and prints nothing on stdout when the
database has no MCP service, no `uri` yet or an empty token, so the
recipe below stops on its exit status and needs no further check. The
values stay in a shell variable, so no file holds the token.

**Example:**

```bash
mcp=$(pgedge starfleet managed database mcp connection \
    e5f6a7b8-c9d0-1234-efab-567890123456 -o json)
rc=$?
if [ "$rc" -ne 0 ]; then
  exit "$rc"
fi
uri=$(printf '%s' "$mcp" | jq -r .uri)
token=$(printf '%s' "$mcp" | jq -r .token)

curl -sS --fail "$uri" \
  -H "Authorization: Bearer $token" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize",
       "params":{"protocolVersion":"2024-11-05","capabilities":{},
       "clientInfo":{"name":"curl-example","version":"1.0"}}}'
```

`--fail` is what makes that a readiness check. Without it `curl` exits
0 on a 401 or a 503 and prints the error body, so a service that is
deployed but not yet answering reads as ready.

## RAG

A deployed pipeline accepts requests one segment below the RAG
service's own `uri`, at `POST <uri>/pipelines/<name>`, where the `uri`
is `https://<domain>/rag/v1` and `<name>` is the pipeline's own `name`
from `--pipeline-config`.

A deployed pipeline answers a request that carries no credential. The
RAG configuration has no token field, neither among the deploy and
update flags nor in what `database get` returns, and nothing in front
of the endpoint asks for one: a plain `curl` with no Authorization
header answers 200 with an answer quoting the database's own rows,
while `POST <uri>` on the MCP service at the same hostname answers 401.
An unknown pipeline name answers 404 naming the condition, so pipeline
names can be enumerated. The service's allowlist is therefore the only
guard on a pipeline: treat anything a pipeline can retrieve as readable
by every address that allowlist admits, and keep the list narrow. Each
request spends the tenant's own embedding and completion credits on the
keys supplied at deploy time, keys the API never returns. RAG has no
readiness handshake, so a first request that fails straight after a
deploy or an update is retried rather than read as a broken pipeline.
